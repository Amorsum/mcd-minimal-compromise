# 架构（architecture）

## 1. 总览

```
用户在宿主中表达需求
      │
      ▼
┌─────────────────┐   ┌──────────────────────────────┐
│ Skill（宿主中）  │   │ 官方麦当劳 MCP（mcp.mcd.cn）   │
│ 意图提取/追问/   │──▶│ 门店/菜单/套餐详情/优惠/算价   │
│ 解释/多轮更新    │◀──│ （唯一价格来源）               │
└────┬────────────┘   └──────────────┬───────────────┘
     │ 脱敏标准化数据                  │ 原始返回
     ▼                               ▼
┌─────────────────────────────────────────────┐
│ 本地计算引擎 src/mcd_compromise（无凭证）      │
│  normalize → candidates → constraints →      │
│  compromise ⇄ quote_state（两阶段协议）       │
└─────────────────────────────────────────────┘
```

宿主直接连接官方 MCP；Skill 把**脱敏后的标准化数据**交给本地脚本，再根据脚本返回的候选调用官方试算。**计算脚本不接收 Token**。

## 2. 模块职责与边界

| 模块 | 负责 | 边界（不做什么） |
|---|---|---|
| Skill | 意图提取、必要追问、工具调用顺序、解释、多轮更新 | 不编造价格、商品编码或券规则 |
| MCP 适配层（plan_cli/normalize） | 官方参数映射、结果解析、错误分类、数据脱敏 | 不把内部字段名当作官方字段名 |
| 标准化层（normalize） | 套餐展开、变体、选项、来源标记、品类标注 | 未知选项不视作合法替换 |
| 计算引擎（candidates/constraints/compromise） | 枚举候选、条件检查、妥协比较、去重 | 不依赖模型自由心算 |
| 试算管理（quote_state） | 请求去重、调用预算、报价状态、失败恢复 | 未成功试算的候选不进已核验列表 |
| 会话状态 | 需求版本、选定门店、候选与证据 | 首版只做当前会话记忆 |

## 3. 关键设计决策

### 3.1 金额一律整数分

官方菜单价格为元字符串（"33.5"），报价返回为分。解析用 `Decimal`，杜绝二进制浮点误差；diffPrice 带符号（"- ¥0.5"）也走同一解析器。

### 3.2 约束的三个独立维度

- **生效强度** strength：hard（当前必须满足）/ soft（仅排序偏好）；
- **可讨论性** negotiability：locked（不可讨论）/ ask（可建议，未经接受不生效）/ open；
- **优先级** priority：多个可讨论条件中先讨论哪个（数值小者先）。

三者正交：「25 元以内」是当前硬条件且可讨论；「不要薯条」是硬条件且锁定；「优先用券」是偏好。用户强调「绝不/必须保留」时保守设 locked。

### 3.3 条件评价三态

satisfied / violated / **unknown**。关键规则：

- 报价失败或无效 → 预算条件记 unknown（不是 violated，更不是 satisfied）；
- 品类无法判定（unknown）或近似品类（fries_like 对 fries）→ 排除条件记 unknown；
- 包含未知硬条件的候选**不进入**「全部满足」列表；
- 营养缺失不当零。

### 3.4 报价前剪除只针对锁定条件

可讨论条件的违反候选必须保留——它们正是妥协方向的来源（「允许薯条」「换主食」）。只有锁定条件的违反候选才在报价前剪除，节省试算预算。

### 3.5 两阶段报价协议

```
plan_next() ──▶ quotes_pending（nextActions 含 calculate-price 完整参数）
                     │ 宿主报价并写回 quotes
                     ▼
                 重新 plan_next() ──▶ 终态
```

调度策略：

- **首批 8、单轮 24**（项目配置，非官方承诺）；
- 按相关性分层：原需求可行候选 → 各妥协方向候选 → 其余；
- 已有已核验方案即停止新增试算（有证据即收手，不追求宣称全局最优）；
- 同一候选按 `candidateKey` 去重复用。

### 3.6 最小妥协算法

1. 候选池 = 原需求候选 + 放松全部可讨论条件后的基础空间候选（文档 6.6：删除式检测必须在相同基础菜单空间重新生成，不能沿用已过滤候选）；
2. 无已核验方案时，对**实际造成违反**的可讨论硬约束逐个构建「只改变一个条件」的修改请求；不足时才尝试成对；
3. 排序（可解释，无加权混分）：拒绝违反锁定 → 改动条件数量 → 用户优先级 → 改动幅度 → 试算总价 → 偏好 → 候选键（保证确定性）；
4. 每个方案记录条件差异（proposedChanges），可供程序验证。

某条件在所有已评价候选中都是 unknown（如营养数据缺失）时，**不**建议「取消该条件」，而是报 data_incomplete——数据缺失不能被包装成一种妥协选项。

### 3.7 搜索边界显式声明

单门店/自取/一人/一份主食+零一饮料+零一小食/合法套餐组合。排除多人分餐、跨订单拆单、未知替换、大型分享餐。边界写入每次输出的 `searchScope`，未完整覆盖时 `coverage.truncated=true` 并附说明——不把有限搜索说成覆盖所有可能点法。

## 4. 数据流细节

### 4.1 标准化（normalize）

- `query-meals` → `MenuItem`（含品类标注：category/tag_basis/tag_confidence）；
- `query-meal-detail` → `ComboDetail`（rounds→choices→modification 分组，保留 selectedKey/unselectedKey）；
- `query-store-coupons` → `Coupon`（按券 ID 分组；券商品补成特殊 MenuItem，tags 含「券商品」，只能经优惠变体生成）；
- 品类标注规则按顺序首个命中生效，记录命中关键词与置信度；「扭扭薯」类近似品类标 fries_like/medium，使「不要薯条」对其记 unknown 而非满足。

### 4.2 候选生成（candidates）

- 套餐变体：默认搭配 + 特制去除（不要某酱料）+ 单轮替换（每轮最多 3 个候选，按 |diffPrice| 升序）；**每一轮选择都需通过过滤**（修复过「换饮料变体隐含默认薯条」的缺陷）；
- 单点：主食 alone / +饮料 / +小食 / +饮料+小食；
- 券变体：券商品必须携带券引用（修复过「券商品被当成 0 元单品生成」的缺陷）；
- 规范化键去重；组内按标价估计排序（**只排序不剪除**——没有可靠价格下界时不能按标价剪除，优惠可能改变结果）。

### 4.3 评价（constraints）

`expand_candidate` 把候选展开成具体餐品条目（套餐按轮次展开，记录特制选中状态），再逐条约束三态评价，汇总 hard_pass / locked_pass / violations / unknowns / soft_scores。

## 5. 失败与缓存

- 认证失败：结束本轮实时查询，提示检查本地配置；不要求用户粘贴 Token；
- 限流：有限退避、降并发、保留已有成功结果；
- 报价超时/无效：标记未知，不用估价替代；
- 缓存：菜单按账号+门店+方式+时间短时缓存；个人优惠隔离；报价仅本轮复用，用户选定后重新试算；
- 日志：只记必要状态、耗时与脱敏错误；不记 Token、手机号、精确地址；
- 凭证：环境变量或宿主安全配置；真实响应样本不入库（`examples/real` 已脱敏）。

## 6. 测试策略

- **固定基准**：人工构造的小型菜单（`tests/fixtures/small_menu.json`），结构复刻官方返回；
- **单元**：金额解析、品类标注、展开、三态评价、剪除规则；
- **场景**：可行/隐藏薯条/预算冲突/锁定条件/报价失败/预算上限/营养缺失/多轮保留/版本绑定/确定性/去重（对应实现路径文档第 11 节验收表）；
- **真实联调**：独立运行，见 `validation-report.md`；模拟算价器复刻官方行为（含 600012 与空清单陷阱）。
