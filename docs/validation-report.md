## 2. 测试环境与方法

  - `e2e-request.json` / `e2e-result-1.json`（首批 8 候选）/ `e2e-result-2.json`（二批 16 候选）/ `e2e-result-3.json`（终态）；
  - `e2e-feasible-request.json` / `e2e-feasible-result-1.json` / `e2e-feasible-result-2.json`（可行场景）；
  - `e2e-followup-request.json` / `e2e-followup-result-1.json`（多轮第二轮）、`e2e-turn3-request.json` / `e2e-turn3-result.json`（多轮第三轮）；
  - `nutrition-foods.json`（`list-nutrition-foods` 真实返回全量 160 条）与 `e2e-nutrition-*.json`（营养联调五轮过程文件，见 3.5）。

## 3. 真实数据端到端联调结果

场景需求（两个场景相同，仅预算不同）：**一个牛肉汉堡 + 一杯饮料 + 不要薯条（锁定）**，预算分别为 25 元 / 40 元。

### 3.1 冲突场景（预算 25 元）→ `compromise_proposed`

协议推进：首批 8 候选报价 → 二批 16 候选报价（预算 24 用尽，26 个候选中 24 个已核验）→ 终态。

真实官方报价（单位：分）：

| 候选 | 官方价格 |
|---|---|
| 巨无霸三件套（小食换小杯玉米杯+可乐中杯） | 3600 |
| 巨无霸三件套（小食换 5块心形薯饼+可乐中杯） | 3750 |
| 巨无霸三件套（小食换月下相思扭扭薯+可乐中杯） | 3800 |
| 巨无霸 + 雪碧 / 可乐 | 3500 |
| 麦辣鸡腿汉堡 + 雪碧 / 可乐 | 3200 |
| 板烧鸡腿堡 + 雪碧 | 3300 |
| 板烧鸡腿堡 + 可乐 | 3300 |
| 麦香鸡中套餐 + 雪碧 / 可乐 | 3750 |
| 麦辣鸡腿汉堡三件套 + 雪碧 / 可乐 | 4300 |
| 板烧鸡腿堡三件套 + 雪碧 / 可乐 | 4400 |
| 巨无霸 / 麦辣鸡腿汉堡 / 板烧鸡腿堡 / 麦香鸡中套餐（单点） | 2550 / 2250 / 2350 / 2800 |
| 全部含「王牌小食拼」券候选（5 个） | 失败 600012 |

**结论**：25 元内不存在同时满足四项条件的方案（最便宜的牛肉汉堡+饮料组合为 35.00 元）。
引擎给出唯一最小妥协方案 **C1：巨无霸 + 雪碧，35.00 元**——只改动一个条件
（预算 25.00 → 35.00，按试算价），牛肉汉堡、饮料、不要薯条全部保留，
且明确提示「搜索范围不完整（受试算预算限制），冲突结论仅限已核验候选」。

### 3.2 可行场景（预算 40 元）→ `feasible`

同一门店、同一候选池，首批 8 个候选报价后即出现已核验方案，引擎按设计停止新增试算：

- **P1：巨无霸 + 雪碧，35.00 元**
- **P2：巨无霸 + 可乐，35.00 元**
- **P3：巨无霸三件套（小食换小杯玉米杯、可乐中杯），36.00 元**

三项条件（牛肉汉堡、饮料、不要薯条）均满足，价格均经官方试算。
注意 P3 的展开项包含「小杯玉米杯」——套餐第二轮的隐藏组成只有展开 `rounds` 才能识别，
名称里看不到（见 MCP_INTEGRATION.md 4.1）。

### 3.3 协议行为核验

- **预算纪律**：首批 8、其后每批不超过剩余额度（24−8=16），用尽后不再派单；
- **阶段零停止**：出现已核验方案后不再新增试算（可行场景仅 8 次报价即收敛）；
- **锁定剪除**：含默认中薯条的巨无霸三件套在候选生成阶段即被「不要薯条」排除，未浪费报价；
- **确定性**：同一输入重复运行，候选键排序与方案排序完全一致；
- **诚实边界**：2 个未报价候选（预算用尽）在终态中显式标注 `truncated` 与说明。

### 3.4 多轮对话真实联调（三轮递进）

同一门店、同一菜单快照（`fetchedAt` 一致），模拟真实用户在冲突后的两轮追问，
每轮只更新约束（其余条件保留），**跨轮复用第一轮已核验的 24 条报价**（按 `candidateKey`
去重，第二轮、第三轮均零新增真实报价即达终态）：

| 轮次 | 用户输入（约束变化） | 终态 | 结果 |
|---|---|---|---|
| 第一轮 | 预算 25（可讨论）+ 牛肉汉堡 + 饮料 + 不要薯条（锁定） | `compromise_proposed` | C1：巨无霸+雪碧 **35.00**（预算 25→35，其余保留） |
| 第二轮 | 「35 超了，预算就 25 不能动，汉堡可以换（牛肉优先）」 | `not_found` | 无解；`closestOptions` 给出两条代价路径：**35.00 留巨无霸**（仅超预算）/ **32.00 换麦辣鸡腿汉堡**（超预算+换主食） |
| 第三轮 | 「那 32 就 32」：预算 32 锁定，主食开放 | `compromise_proposed` | C1：麦辣鸡腿汉堡+雪碧 **32.00**（只换主食，预算不动） |

核验点：

- **条件保留**：后两轮仅改动被讨论的条件，饮料与不要薯条（锁定）全程生效；
- **报价复用**：`candidateKey` 跨轮去重生效，重复购物车不重复消耗官方接口；
- **诚实降级**：第二轮如实回答「这家店 25 元内买不到汉堡+饮料」，并给出最接近的已核验
  选项与各自违反的条件（`violatedConstraints`），不编造方案；
- **确定性**：第二轮、第三轮各重复运行一次，输出逐字节一致。

### 3.5 营养约束真实联调（热量上限三轮递进）

门店 1950640。菜单快照含巨无霸三件套（套餐，已展开详情）与巨无霸单品 + 6 种饮料单品；
营养数据为 `list-nutrition-foods` 真实返回（全量 160 条，样本 `examples/real/nutrition-foods.json`，
请求文件内嵌场景裁剪版 12 条）。两阶段协议 + 跨轮报价复用，共 14 个候选、14 次真实试算：

| 轮次 | 用户输入（约束变化） | 终态 | 结果 |
|---|---|---|---|
| 第一轮 | 就要巨无霸 + 一杯饮料 + 热量≤900 大卡 + 预算 40 | `feasible` | P1 巨无霸+纯悦 **33.00 / 513 kcal**；P2 巨无霸+雪碧 **35.00 / 589 kcal**；P3 巨无霸+阳光柠檬红茶 **35.00 / 598 kcal** |
| 第二轮 | 「热量就 700，多了不行」（锁定） | `feasible` | 同上三方案（均≤700）；**零新增报价** |
| 第三轮 | 「热量就 500，多了不行」（锁定） | `not_found` | 如实无解；`closestOptions`：巨无霸+纯悦（513 kcal，仅超热量）/ 巨无霸单品（513 kcal，超热量且无饮料） |

核验点：

- **真实热量判定**：方案热量由营养表按展开组成汇总（513/589/598 kcal），写入 `satisfiedConstraints` 证据；
  超限时违反证据带实际值（如「组合热量 949 kcal 超过上限 900 kcal」）。
- **官方报价名回退**：P2/P3 的饮料菜单名为「雪碧」「阳光柠檬红茶」（无规格，营养表查不到），
  官方报价返回「雪碧小杯」「阳光柠檬红茶小杯」后精确命中 76/85 kcal——本可判定而未被判定，
  据此修复引擎（见第 4 节，MCP_INTEGRATION.md 4.13）。
- **缺失不当零**：菜单「可乐」的报价名仍无规格，营养缺失 → 该候选热量记 `unknown`，
  不进入已核验列表；第三轮中也未冒充「最接近的选项」（见第 4 节第二条修复）。
- **搜索完整性诚实呈现**：第一轮首批 8 条报价即得可行解（`truncated=true` 有标注）；
  补齐全部 14 条后推荐更新（两个饮料方案替换套餐方案），`truncated` 归 false。
- **确定性**：各轮重复运行输出逐字节一致；营养样本裁剪为场景相关 12 条后复跑，
  结果与全量 160 条完全一致（裁剪不改变任何匹配结果）。

## 4. 真实联调捕获并修复的缺陷

**券 ID 与券编码混淆（已修复）**：端到端联调发现，候选生成把 `couponId` 当作
`couponCode` 传给官方 `calculate-price`。二者是不同的值（见 MCP_INTEGRATION.md 4.8）。
修复：`Coupon` 模型增加 `coupon_code` 字段，`normalize_coupons` 采集官方返回的
`couponCode`，券变体改传正确字段；测试夹具的模拟算价器同步增加双字段校验，
防止回归。修复后测试全部通过。

**`not_found` 信息不足（已改进）**：多轮联调第二轮发现，无解终态只输出干巴巴的
「未找到」，用户无法知道差多少、改什么可能成立。改进：`not_found` 时输出
`closestOptions`（最近失配的已核验参考）与每个方案的 `violatedConstraints`
（违反的条件），按「违反条件组合」分组各取最优——不同代价路径（加钱保留原主食 /
加钱换主食）各展示一条，支撑「改变可比较」。新增回归测试
`test_not_found_reports_closest_options`；真实场景复测见 3.4 第二轮。

**官方报价名未用于营养匹配（已修复）**：营养联调发现，菜单单品名常缺规格（「雪碧」），
而 `calculate-price` 返回的官方商品名带规格（「雪碧小杯」）且与营养表精确一致，
但引擎只按菜单名匹配，导致本可判定的候选被记 `unknown`。修复：报价对象按编码保留
官方名（`productCodeNames`），`NutritionMap.totals_for` 支持官方名回退（仍是官方数据的
精确匹配，零猜测）。新增回归测试 `test_totals_for_falls_back_to_official_quote_name`、
`test_energy_eval_uses_official_quote_name`；真实场景复测见 3.5（P2/P3 由 unknown 变已核验）。

**`closestOptions` 混入未知候选（已修复）**：营养联调第三轮发现，「巨无霸+可乐」
（热量 `unknown`、无任何违反）因违反模式为空被排到「最近失配」第一位——未知不等于
接近满足，这是伪造确定性。修复：`closestOptions` 只收完全已知的候选（无 unknown 硬条件）。
新增回归测试 `test_closest_options_excludes_unknown_candidates`。

## 5. 真实接口失败证据

以脱敏券凭证（无效券 ID/券编码）调用 5 个含「王牌小食拼」券候选，官方均返回：

```json
{"success": false, "code": 600012, "message": "未找到优惠券或已赠送给好友"}
```

引擎按错误码（非文案）分类为 `failed`，这些候选不进入已核验列表，其预算条件记
`unknown`。满足实现路径文档「一次真实或受控模拟的接口失败」的验收要求。

## 6. 缺失数据与已知限制

- **报价预算**：单轮 24 次为项目配置（非官方性能承诺），冲突场景有 2 个候选未及报价，
  终态已显式标注搜索不完整；
- **套餐详情覆盖**：仅查询了巨无霸三件套的详情；麦香鸡中套餐等未展开候选的隐藏组成
  不可见，相关条件记 `unknown`（不当满足也不当违反）；
- **优惠券凭证**：示例中的券 ID/券编码已脱敏，含券候选的真实券价未能在端到端中复测
  （联调阶段已验证：王牌小食拼 2200→1590、中薯条买一送一 2700→1350）；
- **官方返回名不一致**：算价返回的商品名可能与菜单名不同（如「雪碧」→「雪碧小杯」），
  展示层以算价返回为准（MCP_INTEGRATION.md 4.9）；营养匹配在菜单名失配时回退到算价
  返回名（4.13），但无法覆盖全部失配（如报价名「可乐」仍无规格）；
- **营养表覆盖**：`list-nutrition-foods` 160 条与门店菜单单品精确同名率仅 25%，
  未覆盖的餐品（新品、周边、随心选组合等）热量记 `unknown`；提升覆盖率需人工审核映射表；
- **订单与支付**：未接入 `create-order`；本 Skill 只读官方数据、不下单；
- **时间有效性**：以上行为以 2026-10-12 至 10-13 实测为准，官方接口后续可能变化。
